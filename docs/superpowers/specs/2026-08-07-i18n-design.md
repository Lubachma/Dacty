# Spec : interface bilingue fr/en (i18n)

Date : 2026-08-07
Statut : approuvée (mode auto)

## Contexte

Le repo va passer public avec une visée internationale. L'UI est 100 % en français en dur : ~215 chaînes réparties sur ~20 composants/pages, 28 succès (titre + description), les libellés de tiers de ligue, `LANGUAGE_LABELS`, la locale `fr-FR` codée en dur à 5 endroits (dates/nombres), et `<html lang="fr">`. La langue des **textes à taper** (`defaultLanguage`) existe déjà et est un réglage séparé — ce chantier concerne uniquement la **langue de l'interface**.

## Décisions (tranchées, mode auto)

1. **Pas de bibliothèque i18n.** Dictionnaires typés maison + hook `useT()`. L'app n'a ni pluriels, ni ICU, ni chargement dynamique de locales : i18next/FormatJS seraient du poids mort. Cohérent avec le style du projet (zéro dépendance superflue).
2. **Nouveau champ de profil `uiLanguage: 'fr' | 'en'`**, indépendant de `defaultLanguage` (langue des textes). Un utilisateur peut vouloir taper du français avec une UI anglaise.
3. **Défaut = détection navigateur** : `navigator.language` commence par `fr` → `'fr'`, sinon `'en'`. S'applique aux nouveaux profils ET aux profils existants sans le champ (défaut dynamique zod à la lecture). Le pseudo par défaut suit la même détection (`'Joueur'` / `'Player'`).
4. **Succès et tiers** : les définitions portent des objets bilingues `{ fr, en }` (type `LocalizedText`), la couche UI choisit la langue à l'affichage. `src/game/` et `src/achievements/` restent sans couplage à l'i18n. Les ids de tiers (`'argent'`…) et de catégories (`'vitesse'`…) restent des clés de données, inchangés en DB.
5. **Sélecteur de langue d'interface dans Réglages** (FR/EN), persisté via `updateProfile`. Effet immédiat sur tout le rendu (le hook lit le store zustand).
6. **Locale de formatage dérivée** : `'fr-FR'` si fr, `'en-US'` si en — dates (`Intl.DateTimeFormat`) et nombres (`toLocaleString`). Suffixes d'unités (` %`, ` s`, ` j`, ` pts`, ` car.`) dans les dictionnaires.
7. **Pas de gestion de pluriel** (YAGNI confirmé par l'inventaire : aucune chaîne à accord variable).
8. **Tests existants** : les 13 fichiers qui requêtent du texte français reçoivent un helper `setUiLanguage('fr')` en `beforeEach` ; les assertions restent en français (couvre le rendu fr). De nouveaux tests couvrent le rendu anglais, la parité des dictionnaires et la détection.

## Architecture

### Nouveau module `src/i18n/`

```
src/i18n/
├── types.ts       # TranslationKey (union des clés), Params, LocalizedText
├── fr.ts          # dictionnaire français (source de vérité des clés, `as const`)
├── en.ts          # dictionnaire anglais, typé Record<TranslationKey, string> → complétude à la compilation
├── translate.ts   # translate(lang, key, params?) pur : lookup + interpolation {token}
├── detect.ts      # detectUiLanguage(): lit navigator.language, gardé pour non-navigateur → 'en'
└── index.ts       # useT(), useUiLanguage(), localeFor(lang), pick(LocalizedText, lang)
```

- Clés plates en notation pointillée par zone : `nav.training`, `play.start`, `results.replay`, `run.invalidated`… (les succès ne passent PAS par les dictionnaires — voir « Données bilingues »).
- `fr.ts` définit les clés (`as const`) ; `TranslationKey = keyof typeof fr`. `en.ts` est typé `Record<TranslationKey, string>` : une clé manquante ou en trop = erreur de compilation. Un test d'exécution vérifie en plus la parité des jeux de clés et des tokens `{…}` entre fr et en.
- Interpolation minimale : `translate('fr', 'home.welcome', { pseudo: 'Ludo' })` remplace `{pseudo}`. Aucun échappement, aucune logique conditionnelle.
- `useT()` : lit `useSettings((s) => s.profile.uiLanguage)`, retourne une closure `(key, params?) => string` mémoïsée sur `lang`.

### Profil et persistance

- `Profile.uiLanguage: 'fr' | 'en'` (requis dans le type).
- `profileSchema` : `uiLanguage: z.enum(['fr', 'en']).default(detectUiLanguage)` — zod v3 accepte une fonction dans `.default()` : les profils legacy sans le champ obtiennent la langue détectée, pas de migration Dexie nécessaire (champ non indexé).
- `DEFAULT_PROFILE.uiLanguage = detectUiLanguage()` et `pseudo` détecté (`'Joueur'`/`'Player'`).
- `settingsStore.update()` est déjà générique — rien à changer.
- `applyUiLanguage(lang)` dans `settingsStore` (à côté d'`applyTheme`) : pose `document.documentElement.lang`, appelée dans `load()` et `update()`. Déterministe, pas d'effet React supplémentaire.

### Données bilingues

- `LocalizedText = { fr: string; en: string }` dans `src/i18n/types.ts`.
- `AchievementDef.title` / `.description` deviennent `LocalizedText`. Les factories (`wpmAchievement`, map volume) génèrent les deux langues. La DB ne stocke que des ids (`AchievementUnlock.id`) : aucune migration.
- Consommateurs mis à jour : `AchievementsPage`, toast de succès dans `PlayPage` (`result.newAchievements` → `pick(a.title, lang)`).
- `TierBadge` / `tierLabel(tier)` → `tierLabel(tier, lang)` (Bronze/Argent/Or/Platine/Diamant/Challenger ↔ Bronze/Silver/Gold/Platinum/Diamond/Challenger). Callers : `HomePage` (LeagueMini), `ChallengerPage` (progression, historique, toast), `ResultsScreen` (« Nouveau tier atteint »).
- `LANGUAGE_LABELS` reste en **autonymes** (`Français`, `English`, `C`, `Python`) quelle que soit la langue d'interface — convention standard des sélecteurs de langue (révisé pendant le plan).

### Migration des chaînes (~20 fichiers)

Composants : `Layout` (titres d'onglet via `useT()`, alerte persistance, « Chargement… »), `Header` (nav), `RunControls`, `ResultsScreen`, `ErrorBoundary`, `RunHud`, `ToastHost`, `TypingArea` (aria-label), `Sparkline` (aria-label devenu paramètre — il sert aussi pour la précision). Pages : `HomePage`, `PlayPage`, `DevPage`, `ChallengerPage`, `LeaderboardPage`, `AchievementsPage`, `StatsPage`, `SettingsPage` (+ le nouveau sélecteur). Divers : toast « Sauvegarde impossible » dans `runStore` (le store lira la langue via `useSettings.getState()`), `index.html` (`lang="en"`, titre anglais — la valeur runtime est posée par Layout).

## Gestion d'erreurs

- Clé absente : impossible à la compilation (types) ; test de parité en filet supplémentaire.
- Token `{x}` non fourni : laissé tel quel dans la chaîne (visible en test), pas d'exception en production.
- `navigator` indisponible (tests Node, SSR) : `detectUiLanguage()` → `'en'`.

## Tests

- `translate.test.ts` : interpolation, langue inconnue impossible (typage), token manquant conservé.
- `dictionaries.test.ts` : parité des clés fr/en et des tokens par clé.
- `detect.test.ts` : `fr-FR` → fr, `en-US` → en, `de` → en, sans navigator → en.
- `profileRepo.test.ts` : profil frais a un `uiLanguage` détecté ; profil legacy sans champ → parsé avec la langue détectée (stub de `navigator.language`).
- Test de rendu anglais : `setUiLanguage('en')` → nav en anglais, titres d'onglet anglais.
- Helper `src/test/i18n.ts` : `setUiLanguage(lang)` (setState sur le store) — ajouté aux `beforeEach` des 13 fichiers de test existants, assertions françaises inchangées.

## Critères de succès

- Tout le rendu visible passe par les dictionnaires (plus de français en dur dans `src/ui/`, hors contenu corpus).
- Bascule fr ↔ en immédiate et persistée, sans rechargement.
- `npm test` et `npm run build` verts ; couverture fr conservée + couverture en ajoutée.
